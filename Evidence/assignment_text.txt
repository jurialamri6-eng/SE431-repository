SE431 – Software Maintenance and Evolution 
 
Fall-2026 Project Description 
The university has an old Library Management System (LMS). The system is functional but has 
evolved without clear architecture. Each student group works as a software maintenance team and 
is provided with the ~100 LOC legacy codebase for LMS. Their responsibility is to analyze, 
maintain, refactor, and reengineer it. Following is the list of original requirements: 
1. Active members can borrow books. 
2. A member can borrow a maximum of 3 books. 
3. A book can only be borrowed when available. 
4. The normal borrowing period is 14 days. 
5. A fine is charged for late returns. 
6. Members can search for books. 
 
Phase 1: Program comprehension analysis  
This first part involves understanding the given codebase through program comprehension and 
reverse engineering techniques. Students should investigate the existing system without initially 
changing its implementation. They should identify major components, responsibilities, 
dependencies, data flow, business rules, database structure/ schema, existing architectural problems 
and code smells. Expected deliverables include: 
• 
Identify/confirm the given requirements from the code base  
• 
Business rules  
• 
Current architecture diagram 
• 
Class/module responsibility table 
• 
Dependency analysis  
• 
Code-smell identification 
Phase 2: Maintenance  
After having the basic understanding, maintenance requires considering the proposed change 
request one-by-one and do the following for each request: 
• 
Maintenance classification  
• 
Impact analysis  
o Affected components  
o Affected database tables  
• 
Proposed design  
• 
Implementation (bonus marks) 
Maintenance Request: 


--- PAGE 2 ---
 
 
MR-01: The library has purchased multiple copies of each book. The system must support more 
than one available copy. 
MR-02: The university wants to replace the current database implementation. The business 
functionality should remain unchanged.  
 
Phase 3: Refactoring 
The borrow()function has become difficult to maintain. Refactor the system while preserving 
externally observable behavior. This section requires at least two more documented refactoring like 
fixing long methods, mixed responsibilities, direct DB access, primitive data etc.  
 
Phase 4: Reuse & Domain Engineering 
The university wants an Equipment Borrowing System for managing the equipment like laptops, 
projectors, cameras and laboratory instruments. Students must analyze the commonality between 
the two systems in terms of: 
• Common features 
• Variable features 
And propose a reusable domain architecture. 
Phase 5: Quality Evaluation of Reengineered Architecture 
Based on the maintenance problems analyzed in part 1 and reengineered architecture proposed, this 
section includes the quality evaluation of new system architecture that should be evident through 
the following measurements: 
• Lines of Code (LOC)  
• number of functions 
• number of classes 
• cyclomatic complexity 
• code smells 
• DB dependencies 
Phase 6: Git Repository 
For managing your project, start with the basic legacy code and gradually create the commits. 
Your Git repository should include the following:  
01 - Initial legacy system 
02 - Program comprehension analysis 
03 – Maintenance Request incorporation 
04 - Refactor borrowing module 
05 - Add Equipment Borrowing System analysis for re-use 
06 - Final reengineered system 
 
This Git repository/history should be part of the submission, must show the system evolution in a 
sequence as described in various parts of the projects.
